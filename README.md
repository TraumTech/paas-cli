# paas-cli

Универсальный для любого потребителя бинарь, которым получают контракты сервисов
платформы PaaS. Не привязан к стеку потребителя: контракт любого сервиса тянется
одной командой откуда угодно.

## Подключение кластера

```sh
paas-cli clusters connect --name yc-prod            # текущий контекст kubeconfig
paas-cli clusters connect --name yc-prod --context prod --yes
```

Команда спрашивает у платформы, какие права ей нужны, показывает что именно
появится в кластере, и после подтверждения заводит там учётную запись **вашим
же доступом**. Платформе уходит токен этой учётки — ваш личный доступ ей не
передаётся и в неё не попадает.

Повтор безопасен: уже созданное переиспользуется, а права роли приводятся к
тем, что платформа просит сейчас.

## Оператор СУБД в подключённом кластере

```sh
paas-cli databases operators install --engine postgres              # текущий контекст kubeconfig
paas-cli databases operators install --engine postgres --context prod --yes
```

Ставит в **уже подключённый** кластер оператор СУБД (для Postgres —
CloudNativePG), которым платформа дальше заводит СУБД под окружения (DB-05).
Манифест и версию отдаёт платформа: обновление оператора — повтор той же
команды, без новой версии CLI. Установка — административная операция (CRD,
роли, вебхуки), поэтому делается **вашим доступом**; учётной записи платформы
достаётся одно узкое право — на ресурс «кластер СУБД» оператора (роль
`paas-platform-<engine>`). Ни CRD, ни роли платформа трогать не может.

Перед применением команда показывает, что именно появится в кластере, и
спрашивает подтверждение. Повтор безопасен: объекты приводятся к манифесту
server-side apply, и команда говорит, что изменилось (или что менять нечего).

## Установка

**macOS — одной командой.** Платформа отдаёт установщик, который сам определяет
архитектуру (Apple Silicon / Intel), скачивает актуальный релиз и ставит бинарь:

```sh
curl -fsSL https://api.paas.traumtech.ru/cli/install.sh | sh
```

Ставится без `sudo` в `~/.local/bin` (каталог переопределяется переменной
`PAAS_CLI_INSTALL_DIR`); если его нет в `PATH`, установщик подскажет, как добавить.
Версию берёт из последнего
[релиза](https://github.com/TraumTech/paas-cli/releases) через бэкенд платформы.

Альтернативы (любая ОС): готовые бинари (linux/macOS/windows, amd64/arm64) — в
[GitHub Releases](https://github.com/TraumTech/paas-cli/releases). Или через Go:

```sh
go install github.com/TraumTech/paas-cli/cmd/paas-cli@latest
```

Или собрать локально:

```sh
go build -o paas-cli ./cmd/paas-cli
```

Версия бинаря: `paas-cli --version`.

## Релизы

Релизы собирает [GoReleaser](https://goreleaser.com) по git-тегу `vX.Y.Z`
(`.github/workflows/release.yml`): кросс-платформенные бинари и архивы
публикуются в GitHub Releases, версия прошивается в бинарь через ldflags.

```sh
git tag v0.1.0 && git push origin v0.1.0   # триггерит сборку релиза
```

## Использование

Получить **актуальный** опубликованный контракт сервиса и записать его к себе.
Имя сервиса CLI узнаёт у платформы и кладёт контракт в
`<destination>/<service-name>/` **в родном для формата виде** — файл по типу
протокола (тип CLI тоже узнаёт у платформы, объявлять его не нужно):
OpenAPI → `openapi.json`, gRPC → `contract.proto` (тот же `.proto`-исходник,
что опубликован владельцем; стабы из него потребитель генерирует сам):

```sh
paas-cli protocols fetch <service-id>                      # → protocols/<service-name>/openapi.json
paas-cli --destination vendor/api protocols fetch <service-id>   # → vendor/api/<service-name>/openapi.json
```

#### Частичный контракт

Если из контракта нужны лишь отдельные методы, перечисли их по HTTP-паттерну
(`МЕТОД /путь`) флагом `--method`/`-m` (повторяемый или через запятую) — платформа
обрежет контракт до этих операций, CLI получит уже частичный (сужение выполняет
реестр протоколов). Метод сопоставляется без учёта регистра, путь — как в
контракте (вместе с шаблонными параметрами `{id}`). Каждая оставленная операция
сохраняется целиком, а определения, на которые срез больше не ссылается,
отбрасываются: результат самодостаточен и меньше:

```sh
paas-cli protocols fetch <service-id> -m "GET /services" -m "GET /services/{id}"
paas-cli protocols fetch <service-id> --method "GET /services,DELETE /services/{id}"
```

Если указан несуществующий метод, команда сообщает, какой именно не найден, и
ничего не записывает — рабочий контракт не затирается неполным срезом. Набор
методов задаётся явно, поэтому прогон воспроизводим.

Внутри выбранных методов контракт можно срезать до **используемых атрибутов**
флагом `--attribute`/`-a` (PRT-29; требует `--method`): координата — идентичность
атрибута формата (`GET /services#response.200.name` у OpenAPI). В срезе остаются
объявленные атрибуты с цепочками предков и обязательное для вызова (параметры
пути, обязательные параметры и поля тела запроса); метод без объявленных
атрибутов остаётся целиком, общая для методов схема — объединение объявленного:

```sh
paas-cli protocols fetch <service-id> -m "GET /services" -a "GET /services#response.200.name"
```

Несуществующий атрибут — понятная ошибка с перечнем ненайденных, как у методов.
Для формата без поддержки среза до атрибутов (gRPC) явный `--attribute` — ошибка.

Директория для контрактов задаётся глобальным флагом `--destination`/`-d`
(по умолчанию `protocols`). Адрес платформы по умолчанию — прод; переопределяется
переменной окружения `PAAS_API_URL`:

```sh
PAAS_API_URL=http://localhost:8080 paas-cli protocols fetch <service-id>
```

#### Аутентификация токеном (`PAAS_API_TOKEN`)

Для неинтерактивного доступа (CI, скрипты выкатки) `paas-cli` предъявляет платформе
**токен доступа** из переменной окружения `PAAS_API_TOKEN`; если она задана, CLI
прикладывает токен ко всем обращениям к платформе:

```sh
PAAS_API_TOKEN=<секрет> paas-cli protocols publish "$version_id"
```

Токен бывает двух видов, предъявляются они одинаково:

- **токен сервиса** (`paas_pat_…`, эпик «Машинный доступ») — вызов идёт **от имени
  сервиса**: owner-команды выкатки (`versions publish`, `protocols publish`,
  `dependencies register`) выполняются как этот сервис, а управление аккаунтом ему
  недоступно;
- **личный токен пользователя** (`paas_uat_…`, AUTH-18) — вызов идёт **от имени
  человека**, с теми же правами, что у него в браузере. Пользователь заводит его
  сам в разделе «Личные токены» интерфейса; срок действия обязателен — не дольше
  года.

Секрет в обоих случаях показывается один раз. Без `PAAS_API_TOKEN` CLI обращается к
платформе сохранённым входом (`auth login`), а без него — как прежде, анонимно.
Негодный токен платформа отклоняет — команда завершается с понятной ошибкой.

#### Вход под своей учётной записью (`auth`)

Человеку на своей машине токен сервиса не нужен: `paas-cli` умеет входить под
учётной записью платформы (той же, что и в веб-интерфейсе):

```sh
paas-cli auth login                     # откроет браузер: подтвердите вход на странице платформы
paas-cli auth login --password          # прежний путь: e-mail и пароль в терминале (пароль — без эха)
paas-cli auth login -e me@example.com   # e-mail подразумевает вход паролем
paas-cli auth whoami                    # под кем выполнен вход (проверяется у платформы)
paas-cli auth logout                    # завершить вход и удалить его локально
```

**Вход через браузер** (по умолчанию, AUTH-22): CLI поднимает слушателя на
петлевом адресе и открывает страницу подтверждения в интерфейсе платформы, где
вы уже вошли. После подтверждения платформа выпускает **личный токен** и
возвращает его CLI на этот адрес — секрет не покидает машину и не копируется
руками. Токен виден в разделе «Личные токены» под именем, которое вы задали, и
отзывается оттуда; `auth logout` отзывает его тоже. Адрес интерфейса берётся из
`PAAS_WEB_URL` (по умолчанию прод — `https://paas.traumtech.ru`); там, где
браузер открыть нельзя (машина по ssh), остаётся `--password` или личный токен в
`PAAS_API_TOKEN`.

Вход сохраняется локально — в конфиг-директории пользователя
(`~/Library/Application Support/paas-cli/session` на macOS,
`~/.config/paas-cli/session` на Linux; каталог `0700`, файл `0600`) — и
прикладывается ко всем обращениям к платформе, пока не истечёт или не будет
завершён `auth logout`. Пароль через флаг или аргумент не принимается, чтобы
секрет не оседал в истории shell.

Приоритет креденшелов: заданный `PAAS_API_TOKEN` (машинный сценарий CI) всегда
выигрывает у сохранённого входа. Без обоих CLI обращается к платформе анонимно,
но платформа анонимные запросы отклоняет — CLI подскажет войти или задать токен.
Адрес identity-провайдера платформы берётся из `PAAS_AUTH_URL` (по умолчанию
прод — `https://auth.paas.traumtech.ru`).

#### Манифест зависимостей

Чтобы не перечислять сервисы в команде при каждом обновлении, состав зависимостей
объявляется в манифесте `protocols.toml` в корне репозитория потребителя, а
`protocols sync` тянет все объявленные контракты разом. Манифест перечисляет сервисы
**по имени** (не по версии): воспроизводимость даёт git — полученные снимки
коммитятся, — а не пин на эфемерную версию продьюсера.

Манифест **обязательно** объявляет и сам репозиторий — секцией `[service]` (какой
сервис он представляет). Поле `contract` заполняет только репозиторий-владелец,
публикующий протокол (см. «Публикация протокола»); чистому потребителю оно не нужно —
своего контракта он не имеет.

Сервис с **несколькими API-поверхностями** объявляет контракты перечнем
`[[protocols]]` (CLI-23): у каждой записи обязательное имя (alias протокола в
реестре, PRT-21/22), путь к контракту и формат. `contract` в `[service]` — прежняя
форма для единственного контракта (протокол по умолчанию); объявить контракт обеими
формами сразу нельзя.

```toml
[service]
name = "paas-backend"

[[protocols]]
name = "http"                 # alias протокола в реестре
contract = "openapi.json"

[[protocols]]
name = "internal-grpc"
contract = "api/edge.proto"
format = "grpc"
```

```toml
# protocols.toml
# destination опционально (по умолчанию "protocols")
# destination = "protocols"

# Обязательная самодекларация репозитория. contract — только у репозитория-владельца,
# который публикует протокол; у чистого потребителя достаточно name.
[service]
name = "frontend"
# contract = "openapi.json"   # путь к собственному контракту (для публикации)
# format = "grpc"             # формат контракта: openapi (по умолчанию) или grpc

[[dependencies]]
name = "paas-backend"

[[dependencies]]
name = "billing"
methods = ["POST /invoices", "GET /invoices"]   # необязательный частичный контракт (по HTTP-паттерну)
# необязательный срез внутри методов до используемых атрибутов (PRT-29, только OpenAPI):
attributes = ["GET /invoices#response.200.id", "GET /invoices#response.200.total"]

[[dependencies]]
name = "paas-protocols"   # gRPC-продьюсер: методы — идентичностью package.Service/Method
methods = ["traumtech.paas_protocols.v1.RegistryService/PublishProtocol"]
waived = ["traumtech.paas_protocols.v1.Protocol.document"]   # атрибуты, которые мы больше не читаем
```

```sh
paas-cli protocols sync                       # читает ./protocols.toml
paas-cli protocols sync --manifest deps.toml  # другой путь к манифесту (-f)
```

#### Форма сервиса и его адрес

Выкатываемый сервис объявляет в том же манифесте свою **форму** — процессы, из
которых платформа сгенерирует манифесты выкатки. Форма уезжает на платформу
вместе с версией (`versions publish`), поэтому выкатка не зависит от состояния
репозитория. Слушающий процесс может объявить и **маршрут** — доменную зону
организации по имени и префикс под её базовым хостом; адрес вычисляет выкатка,
и он едет с версией, как образ. Маршрутов может быть несколько — по одному на
слушающий процесс.

```toml
[[processes]]
name = "server"
listen = 8080          # отсутствие — воркер: без Service и публичного входа
command = ["./app"]    # обязательно (DEP-22): чем запускается контейнер
cpu = "100m"
memory = "128Mi"
zone = "main"          # доменная зона организации; без неё маршрута нет
prefix = "api"         # пусто — сам базовый хост зоны

[[processes]]
name = "worker"
```

##### Значения окружений

Переменные окружения и число реплик тоже объявляются в манифесте и едут с
версией. Общее — в `[env.default]`, отличия — в `[env.<окружение>]`
(`dev`/`stage`/`prod`):

```toml
[env.default]
replicas = 1

[env.default.variables]
LOG_LEVEL = "info"
OTLP_ENDPOINT = "tempo.paas-observability.svc.cluster.local:4317"

[env.prod]
replicas = 2

[env.prod.variables]
LOG_LEVEL = "warn"          # перебивает общее значение; OTLP_ENDPOINT остаётся
```

- Слияние делает CLI при публикации: версия принадлежит окружению, поэтому
  платформа получает уже готовый набор, а не правило слияния. Переменные
  сливаются по имени — переопределяется только одноимённое значение.
- Секции для неизвестного окружения (`[env.prd]`) отклоняются до обращения к
  платформе: опечатка иначе молча никуда не доехала бы.
- **Секреты в манифест не кладут** — их значения задаются в окружении на
  платформе и в репозиторий не попадают.
- В интерфейсе платформы объявленные значения только показываются: правка
  оттуда молча отменялась бы следующей выкаткой.

- Адрес в окружении = `prefix` + базовый хост зоны в этом окружении. У зоны нет
  базового хоста в окружении — выкатка туда проходит без публичного входа.
- Маршрут, исчезнувший из манифеста, перестаёт обслуживаться со следующей
  выкатки в это окружение; другие окружения не затронуты до их выкатки.
- Сервисы, не объявившие маршрут, адресуются назначением из интерфейса — как
  раньше.

##### Базы данных

Потребность сервиса в базах объявляется списком `[[databases]]` (DB-03) и едет
с формой сборки. Каждая запись называет базу внутри сервиса, тип СУБД и
**подключённую СУБД организации** по имени; окружение может переопределить
только «где заводить», не трогая форму:

```toml
[[databases]]
name = "main"                # имя базы внутри сервиса (kebab-case)
engine = "postgres"          # тип СУБД; СУБД с именем server должна быть того же типа
server = "paas-postgres"     # имя подключённой СУБД организации
# variable = "MY_DSN"     # переменная с доступом; умолчание — POSTGRES_MAIN_URL

[env.dev.databases.main]
server = "dev-pg"            # в dev та же база заводится в другой СУБД
```

- Из имени платформа выводит базу и роль (`<сервис>_<имя>`) и переменную по
  умолчанию по шаблону «тип первым токеном» (`POSTGRES_<ИМЯ>_URL`);
  имя базы опционально — единственную безымянную базу платформа понимает как
  `default`, её база/роль называются по одному сервису, а переменная —
  `POSTGRES_URL` без сегмента имени (DB-07). Переменная не должна быть занята
  переменными окружений манифеста.
- При публикации сборки платформа проверяет, что названная СУБД у организации
  есть и того же типа; что она обслуживает окружение выкатки — проверит
  выкатка (назначение «СУБД → окружение»).
- Выкатка заводит объявленные базы в СУБД окружения и передаёт процессу
  доступы секретными значениями окружения (DB-04).

- Раскладка та же, что у `fetch`: по контракту на сервис в `<destination>/<name>/`,
  в родном виде (`openapi.json` у OpenAPI, `contract.proto` у gRPC). Директорию
  задаёт `destination` в манифесте; явный `--destination`/`-d` её переопределяет.
- На каждую зависимость можно сузить контракт до методов полем `methods` (как `-m` у
  `fetch`); сужение выполняет платформа, CLI получает уже частичный контракт.
  У gRPC-зависимостей методы задаются идентичностью `package.Service/Method` и
  **объявляют используемые методы** для регистрации зависимостей
  (`dependencies register`); срез gRPC-контракта — тоже частичный (PRT-23).
- Полем `attributes` объявляются **используемые атрибуты внутри объявленных
  методов** (PRT-29): координата — идентичность атрибута формата
  (`GET /services#response.200.name` у OpenAPI), снимок сужается до объявленного
  с цепочками предков и обязательным для вызова; метод без объявленных атрибутов
  едет целиком, общая для методов схема — объединение объявленного ими. Требует
  объявленных `methods`. Для gRPC срез до атрибутов платформа пока не
  поддерживает — снимок приносится по методам, о чём прогон честно сообщает.
  В отличие от `waived` перечень управляет снимком (а снимок — кодогенерацией),
  поэтому использовать необъявленное физически нельзя и перечень не гниёт.
- Полем `waived` объявляются **атрибуты продьюсера, от которых мы отказались**
  (идентичность атрибута — `полное.имя.Типа.поле`, у перечислимого типа —
  `полное.имя.Типа.ЗНАЧЕНИЕ`). По умолчанию потребитель зависит от всех атрибутов
  используемых методов, поэтому перечень короткий и не обязан быть полным:
  заводится ровно тогда, когда продьюсеру нужно поле удалить. Отказы уходят в
  платформу при `dependencies register` и принадлежат версии потребителя — новая
  версия объявляет их заново.
- Имя сервиса CLI резолвит в его id у платформы. Если объявленный сервис не найден,
  контракт не получить, либо манифест отсутствует/пуст/неразбираем — команда печатает
  понятную ошибку (с именем упавшей зависимости) и завершается ненулевым кодом,
  останавливая пайплайн; уже полученные рабочие контракты не затираются.

### Гарантии

- **Воспроизводимость.** Повторный прогон после публикации нового контракта
  приносит свежий контракт.
- **Понятные ошибки.** Если контракт не получить (сервис недоступен, не найден или
  контракт ещё не опубликован) — печатается понятная ошибка с ненулевым кодом
  выхода.
- **Не затирает рабочий контракт.** Запись атомарна (временный файл + rename):
  при ошибке/битом ответе ранее полученный контракт остаётся нетронутым.

Кодоген (генерация клиента/типов из контракта) — забота потребителя; CLI только
получает контракт.

### Проверка совместимости контракта-кандидата (для владельца сервиса)

Owner-команда для процесса выкатки: проверить, **ломает** ли контракт-кандидат
зарегистрированных потребителей сервиса — **до** деплоя и **без публикации**.
Платформа сверяет кандидата со снимком каждого потребителя и возвращает разбор;
команда печатает его и завершается ненулевым кодом, если кандидат ломающий.

```sh
paas-cli protocols compatibility                                 # без аргументов: все контракты манифеста (CLI-23)
paas-cli protocols compatibility <service-id> <candidate-file>   # точечный режим, напр. ./openapi.json
paas-cli protocols compat <service-id> <candidate-file>          # короткий алиас
paas-cli protocols compat --format grpc <service-id> registry.proto   # gRPC-кандидат (.proto)
paas-cli protocols compat --name admin <service-id> admin.json   # кандидат именованного протокола
```

**Без аргументов — манифестный режим**: проверяются все контракты из манифеста
(перечень `[[protocols]]` либо `contract` в `[service]`), каждый — против
потребителей своего протокола; путь к манифесту — `--manifest`/`-f`. Ломающий
кандидат любого протокола — ненулевой код выхода. Перед сверками действует **гейт
исчезнувшего протокола**: протокол, живущий в реестре, но пропавший из манифеста
(в том числе после переименования имени), с потребителями — ошибка, без — только
предупреждение.

В точечном режиме формат кандидата задаёт флаг `--format` (`openapi` по умолчанию —
существующие пайплайны без изменений, или `grpc` — кандидат читается как
`.proto`-исходник), имя протокола — `--name` (пусто — протокол по умолчанию).
Неподдерживаемый формат — понятная ошибка до похода на платформу.

- По каждому потребителю видно, какую его версию затрагивает кандидат, что меняется
  и что из этого ломающее.
- **Нет потребителей** → «кандидат никого не затрагивает», код выхода `0`.
- **Ломающий кандидат** → ненулевой код выхода: пайплайн CI/CD останавливается
  до деплоя. Совместимый → код `0`.
- Несравнимый снимок потребителя ломающим не считается.
- Пустой/неразбираемый файл кандидата, недоступная платформа или ненайденный сервис
  — понятная ошибка (отличимая по выводу от вердикта «ломает»).

Проверка **ничего не публикует и не меняет реестр** — её можно прогонять сколько
угодно раз.

### Публикация протокола (для владельца сервиса)

Owner-команда для процесса выкатки: опубликовать протоколы сервиса под версией.
Какой это сервис и где его контракты в репозитории — берётся из манифеста (перечень
`[[protocols]]` либо `contract` в `[service]`), а не повторяется в команде;
аргументом приходит только версия. Публикуются **все объявленные контракты**, каждый
под своим именем и к той же версии — версия несёт все свои API-поверхности, выбора
«какой именно» в CI нет. Контракты читаются из **локальных файлов репозитория**, а
не выкачиваются из запущенного сервиса. Платформа привязывает протоколы к версии и
возвращает разбор совместимости с потребителями, который команда печатает по каждому.

```sh
paas-cli protocols publish <version-id>                     # сервис и контракт — из ./protocols.toml
paas-cli protocols publish --manifest deps.toml <version-id># другой путь к манифесту (-f)
```

- Версию (`<version-id>`) даёт предыдущий шаг выкатки — публикация версии по
  развёрнутой ревизии (см. roadmap эпика CLI).
- Имя сервиса из `[service]` CLI резолвит в его id у платформы; контракт берётся по
  пути `contract` относительно манифеста. Нет секции `[service]` (или в ней нет имени
  либо пути) — понятная ошибка с ненулевым кодом.
- Формат контракта задаёт поле `format` в `[service]`: `openapi` (по умолчанию —
  манифесты без поля работают как прежде) или `grpc` (`contract` указывает на
  `.proto`-исходник). Неподдерживаемое значение — понятная ошибка до похода на
  платформу. Синтаксис `.proto` проверяет платформа; CLI лишь не отправляет пустой
  файл.
- Сверки совместимости для gRPC-контрактов пока нет: в сводке потребители такого
  протокола помечаются «не сверялось», публикацию это не удерживает.
- Перед публикацией действует **гейт исчезнувшего протокола** (CLI-23): протокол,
  живущий в реестре, но пропавший из манифеста (в том числе после переименования
  имени — для реестра это «старый исчез, новый появился»), с потребителями —
  ошибка до первой публикации (верните запись либо снимите зависимость
  потребителей), без потребителей — предупреждение в сводке.
- Все контракты читаются и проверяются **до первой публикации** — опечатка в любой
  записи не оставляет перечень опубликованным наполовину.
- После публикации печатается сводка совместимости: по каждому потребителю — какую
  его версию затрагивает контракт, что меняется и что из этого ломающее.
- **Нет потребителей** → «публикация никого не затрагивает».
- Сводка **только информирует**: ломающее изменение не делает команду неуспешной
  (код выхода `0`) — гейт ломающих изменений живёт в проверке совместимости
  (`protocols compatibility`) до деплоя.
- Пустой/неразбираемый файл контракта, недоступная платформа, ненайденный сервис или
  версия — понятная ошибка с ненулевым кодом выхода.

### Публикация версии (для владельца сервиса)

Owner-команда для процесса выкатки: по факту выкатки зафиксировать в реестре новую
версию сервиса, привязанную к развёрнутой ревизии коммита. Имя сервиса берётся из
секции `[service]` манифеста; аргументом приходит только ревизия. Заменяет
самодельный `curl`-шаг пайплайна.

```sh
paas-cli versions publish <commit-revision>   # напр. "$GITHUB_SHA"; сервис — из ./protocols.toml
```

- **Версия принадлежит окружению (DEP-08):** флаг `--environment` (`-e`) —
  `dev`, `stage` или `prod`; без флага — `prod`, поэтому существующие
  пайплайны продолжают работать без правок. Нумерация версий своя в каждом
  окружении, выкатывается версия только в своё окружение.

- **Ветка сборки (DEP-17):** флаг `--branch` — ветка, из которой собрана версия
  (в CI это ref сборки, например `${{ github.ref_name }}`). Флага нет — платформа
  ветку не знает и не выдумывает: «неизвестно» честнее подставленной основной.
  Сам CLI git не читает: в CI рабочая копия бывает detached, и «текущая ветка»
  там врёт.

  ```sh
  paas-cli versions publish --branch "$GITHUB_REF_NAME" "$GITHUB_SHA"
  ```

- **Идентификатор версии печатается на stdout** отдельной строкой — его без разбора
  подхватывает следующий шаг выкатки (например, привязка протокола к версии):

  ```sh
  version_id=$(paas-cli versions publish "$GITHUB_SHA")
  ```

  Человекочитаемое подтверждение уходит на stderr, чтобы не мешать автоматике.
- **Идемпотентно**: одна ревизия — одна версия. Повторный прогон с той же ревизией
  («Re-run» пайплайна) возвращает ту же версию с тем же id, а не создаёт дубликат.
- Имя сервиса резолвится в id у платформы. Пустая ревизия, отсутствие секции
  `[service]` в манифесте, недоступная платформа или ненайденный сервис — понятная
  ошибка и ненулевой код выхода (id на stdout не печатается).

### Регистрация зависимостей версии от контрактов (для потребителя)

Команда потребителя для процесса выкатки: объявить в реестре весь состав зависимостей
зафиксированной версии прямо из манифеста. Продьюсеров команда берёт из объявленных
зависимостей (резолвит по имени), а снимки их контрактов — из раскладки контрактов
репозитория (та же, что наполняет `sync`: `<destination>/<producer>/openapi.json`).
Аргументом приходит только версия. Обобщает регистрацию по одной зависимости в один
прогон по всему манифесту, заменяя самодельный `jq`+`curl`-шаг пайплайна.

```sh
paas-cli dependencies register <version-id>           # состав — из ./protocols.toml
paas-cli dependencies register --prune <version-id>   # + снять прошлые версии этого потребителя
```

- `<version-id>` — версия своего сервиса-потребителя (id даёт `versions publish`).
  Потребитель — из секции `[service]` манифеста; продьюсеры и снимки — из его
  зависимостей и раскладки контрактов.
- Снимок каждой зависимости — закоммиченный контракт продьюсера, на котором собрана
  версия; команда не сужает его по `methods` — берёт с диска как есть (срез уже
  применил `sync`).
- `--prune` — для потребителя, который деплоится в одно окружение: каждая
  зарегистрированная зависимость замещает зависимости прошлых версий этого потребителя
  от того же продьюсера, оставляя в реестре только эту версию. Само снятие делает
  платформа атомарно с регистрацией — отдельный шаг снятия из выкатки больше не нужен.
- **Идемпотентно**: повторный прогон обновляет снимки тех же зависимостей, а не плодит
  дубли («Re-run» пайплайна безопасен); с `--prune` повторный прогон даёт то же
  состояние (одна актуальная версия).
- Отсутствие секции `[service]` или зависимостей в манифесте, недоступный снимок,
  недоступная платформа, ненайденная версия, потребитель или какой-то продьюсер —
  понятная ошибка (с именем упавшей зависимости) и ненулевой код выхода; на полпути
  состав не регистрируется.

## Наблюдаемость

CLI инструментирован `paas-observability-sdk`: каждая команда открывает
корневой спан (имя — путь команды, например `protocols sync`), HTTP-запросы к
платформе становятся его дочерними спанами, а `traceparent` уходит с запросами
дальше — в Grafana Tempo видна сквозная трасса CLI → платформа.

Трассы отправляются по OTLP/HTTP в приёмный шлюз платформы (тот же, что
принимает трассы браузера):

- `PAAS_OTLP_URL` — адрес шлюза (по умолчанию `https://otlp.paas.traumtech.ru`);
  значение `off` выключает трассировку. Без сети команда не зависает: ретраи
  выключены, на досылку спанов при завершении отведено 3 секунды.

Диагностические логи пишутся в stderr и по умолчанию не мешают выводу команд
(уровень `WARN`, человекочитаемый формат):

- `OBSERVABILITY_LOG_LEVEL` — `DEBUG`/`INFO`/`WARN`/`ERROR`; `INFO` показывает
  каждый HTTP-запрос к платформе (метод, путь, статус, длительность, trace_id);
- `OBSERVABILITY_LOG_ENCODING` — `PLAIN` (по умолчанию) или `JSON` (для CI).

Метрики CLI не собираются: процессу-однодневке некому их отдавать (pull-модель),
вместо реализации SDK подставлена заглушка. Observer собран в composition root
вручную из компонентов SDK (`internal/app/observability.go`): пресет
`observabilitydefault` рассчитан на сервисы — поднимает Prometheus HTTP-сервер и
экспортирует трассы только по OTLP gRPC, а внешний шлюз принимает OTLP/HTTP.

## Архитектура

Чистая архитектура (см. `../../docs/go-architecture.md`), адаптированная под CLI:

- `internal/entities` — `Protocol`, `CandidateContract`, `CompatibilityReport`,
  `Version` и доменные ошибки;
- `internal/usecases` — use cases `FetchProtocol` / `CheckCompatibility` /
  `PublishVersion` и интерфейсы зависимостей (`ProtocolSource`, `ProtocolStore`,
  `CandidateReader`, `CompatibilitySource`, `VersionPublisher`);
- `internal/entities` — `Protocol`, `CandidateContract`, `CompatibilityReport`,
  `ProtocolPublication` и доменные ошибки;
- `internal/usecases` — use cases `FetchProtocol` / `CheckCompatibility` /
  `PublishProtocol` и интерфейсы зависимостей (`ProtocolSource`, `ProtocolStore`,
  `CandidateReader`, `CompatibilitySource`, `ProtocolPublisher`);
- `internal/controllers/protocol_fetch_command_cli` — подкоманда `protocols fetch`,
  `internal/controllers/protocol_compatibility_command_cli` — подкоманда
  `protocols compatibility`, `internal/controllers/protocol_publish_command_cli` —
  подкоманда `protocols publish` (input-адаптеры на [urfave/cli v3](https://cli.urfave.org));
- `internal/adapters/protocol_source_http` / `protocol_compatibility_http` /
  `protocol_publish_http` — обращение к API платформы через сгенерированный клиент
  `pkg/platformapi`;
  `protocols compatibility`, `internal/controllers/version_publish_command_cli` —
  подкоманда `versions publish` (input-адаптеры на [urfave/cli v3](https://cli.urfave.org));
- `internal/adapters/protocol_source_http` / `protocol_compatibility_http` /
  `version_publisher_http` — обращение к API платформы через сгенерированный клиент
  `pkg/platformapi`;
- `internal/adapters/protocol_store_file` — атомарная запись протокола в файл,
  `internal/adapters/candidate_reader_file` — чтение файла контракта с диска;
- манифест зависимостей: `entities.Manifest` + use case `SyncProtocols`
  (интерфейсы `ManifestReader`, `ServiceResolver`); подкоманда
  `internal/controllers/protocol_sync_command_cli` (`protocols sync`);
  адаптеры `internal/adapters/manifest_reader_file` (разбор `protocols.toml`) и
  `internal/adapters/service_resolver_http` (резолв имени сервиса в id);
- `internal/app` — composition root: сборка команд и запуск;
- `pkg/platformapi` — клиент API платформы, **сгенерированный из контракта**
  ([oapi-codegen](https://github.com/oapi-codegen/oapi-codegen)).

## Догфудинг контракта

`paas-cli` — сам потребитель API бэкенда, поэтому клиент платформы не пишется
руками, а генерируется из контракта, полученного этим же `paas-cli`:

```sh
paas-cli protocols fetch <paas-backend-service-id>   # → protocols/paas-backend/openapi.json
go generate ./...                                    # контракт → pkg/platformapi + моки
```

И контракт (`protocols/paas-backend/openapi.json`), и сгенерированный клиент
(`pkg/platformapi/platformapi.gen.go`) закоммичены — сборка не требует ни сети, ни
повторной генерации.

go generate ./...   # клиент платформы (oapi-codegen) + моки (go.uber.org/mock)
